# Personal Game Hub — Техническое задание

## 1. Что реализуем

Personal Game Hub — приватный статический веб-сайт из нескольких страниц для одного пользователя, который объединяет три вещи:

1. **Библиотека** — уже готовый список всех игр из Playnite (текущий `index.html`с данными из `games.json`, не меняется, трагать его не надо).
2. **Скидки и вишлист** — автоматическое отслеживание цен на игры из вишлиста Steam/GOG во всех
   официальных магазинах и в магазинах ключей (Instant Gaming и, в перспективе, другие), с историей
   цен и уведомлениями в Telegram, когда достигается выгодная цена.
3. **Рекомендации** — персональный подбор игр на основе оценок и наигранного времени из Playnite, с
   отдельным блоком "неожиданных находок" вне обычного вкуса, и отдельным блоком новинок от
   разработчиков, которых пользователь уже любит.

Сайт полностью статический: никакого постоянно работающего сервера нет и не будет. Все вычисления
(сбор цен, скрейпинг, построение рекомендаций, отправка уведомлений) выполняет Python-пайплайн,
который по расписанию запускает GitHub Actions, а результат — обычные JSON-файлы, которые читает
фронтенд. Это осознанное архитектурное решение: обновлять данные достаточно несколько раз в день,
постоянный бэкенд для этого не нужен, а вся схема остаётся полностью бесплатной.

Проект однопользовательский: без регистрации, без ролей, без записи данных через фронтенд — сайт
только читает и показывает то, что собрал пайплайн.

## 2. Архитектура и принцип работы

```
[Playnite] --(плагин, кнопка)--> games.json (коммит в корень репозитория. это делает пользователь вручную)
                                        │
                                        ▼
                     ┌──────────────────────────────────────┐
                     │   GitHub Actions (CRON + push-триггер) │
                     │   scripts/main.py — оркестратор        │
                     └──────────────────────────────────────┘
        │ читает            │ читает/пишет         │ пишет
        ▼                    ▼                       ▼
  games.json          data/wishlist.json      data/generated_hub.json
  (без изменений)     data/price_cache.json   data/notified_deals.json
                                        │
                                        ▼
                         git commit + push (только data/*.json)
                                        │
                                        ▼
                    Vercel: авто-редеплой статического сайта
                     index.html / hub.html / deals.html / recommendations.html
                                        │
                                        ▼
                              Telegram-бот (уведомления о скидках)
```

**Принцип работы по кругу:**
1. Периодически пользователь вручную с помощью уже написанного плагина для Playnite выгружает данные о имеющихся у пользователя играх и пушит их в `games.json` в
   корень репозитория.
2. По расписанию Cron или при пуше пользователем `games.json` запускается GitHub Actions workflow.
3. Python-пайплайн (`scripts/main.py`) последовательно вызывает модули: подтягивает вишлисты,
   собирает цены (официальные магазины + магазины ключей), пересчитывает рекомендации, формирует
   единый `data/generated_hub.json`, при необходимости шлёт уведомления в Telegram.
4. Изменённые файлы в `data/` коммитятся обратно в репозиторий тем же workflow.
5. Пуш в `main` автоматически триггерит редеплой статики на Vercel — сайт обновляется без
   какого-либо ручного участия.

## 3. Жёсткие ограничения проекта

* Полностью бесплатно: GitHub Free + Vercel Hobby + бесплатные тиры внешних API, без банковских карт.
* `index.html` не изменяется вообще, ни единой строки. Все новые страницы — отдельные файлы.
* `Main.psm1` можно только **дополнять новыми полями экспорта**, ничего в нем не
  удалять и не переименовывать — существующая логика ручного плагина должна продолжать работать как есть.
* `games.json` живёт в корне репозитория (не в `data/`) — это уже существующий контракт, который
  менять нельзя, только расширять. Там собираются данные о имеющихся играх у пользователя и их метаданные.
* Реализация — пошаговая: каждый крупный этап (список — раздел 15) согласовывается перед началом
  следующего, а не реализуется одним большим коммитом.
* Алгоритм рекомендаций не должен быть тривиальным совпадением 2-3 тегов — требуется полноценный
  многофакторный движок (раздел 8), включая рекомендации вне привычного вкуса.
* Каждая рекомендованная и отслеживаемая по вишлисту игра должна показывать график истории цены.

## 4. Приватность и хостинг

Главный приоритет приватности — закрыть **код пайплайна и все секреты** (API-ключи, OAuth-токены,
данные Telegram-бота), а не сами игровые данные (список игр и рекомендации не секретны).

* **Репозиторий приватный.** Это закрывает Python-скрипты, историю коммитов и файл workflow —
  логика пайплайна не должна быть публичной, даже если сами секреты и так замаскированы GitHub.
* **Секреты** хранятся только в GitHub Actions Secrets, как и раньше. Они не появляются ни в коде,
  ни в логах (GitHub маскирует их автоматически), ни доступны через какой-либо публичный API.
* **Фронтенд хостится на Vercel**, а не на GitHub Pages — GitHub Pages бесплатен только для
  public-репозиториев, а нам нужен приватный. Vercel Hobby бесплатно деплоит приватные репозитории,
  если репозиторий принадлежит **личному аккаунту** (`SanchezGamedev`), а не GitHub-организации — это
  единственное условие для бесплатного деплоя приватного репо. При каждом автокоммите данных Vercel
  сам передеплоит статику — отдельный deploy-шаг в workflow не нужен.
* Сайт остаётся открытым по прямой ссылке, без пароля — этого достаточно, раз сами данные не
  секретны. Для базовой защиты от случайного попадания в поисковики добавляется `robots.txt` с
  `Disallow: /` и `<meta name="robots" content="noindex">` на новых страницах.
* На будущее, если понадобится закрыть и сам сайт (например, при передаче ссылки кому-то ещё): это
  добавляется одной маленькой бесплатной Vercel Edge-функцией с HTTP Basic Auth (логин/пароль в
  Vercel Environment Variables). Не требуется для MVP, но архитектура ничего не мешает добавить это
  отдельным шагом позже.

**Бюджет GitHub Actions на приватном репозитории:** 2000 бесплатных минут/месяц. Пайплайн — лёгкий
Python-скрипт, реалистично 2–4 минуты на прогон (если будет чуть больше, это не критично). При расписании раз в 4 часа: 6 запусков/день × 30
дней × ~3 минуты ≈ 540 минут/месяц — запас более чем в 3.5 раза, есть куда расти по частоте запуска
или числу источников данных.

## 6. Контракты данных

### 6.1 `games.json` (корень репозитория, экспорт из Playnite)

Текущие поля (из `Main.psm1`):

| Поле | Тип | Описание |
|---|---|---|
| `Name` | string | Название игры |
| `IsInstalled` | bool | Установлена ли сейчас |
| `UserScore` | number | Оценка пользователя для игры (от 0 до 100, с шагом в 10), если 0 значит пользователь оценку не давал этой игре |
| `Platform` | string | Платформа (обычно "PC") |
| `Developer` / `Publisher` | string | Разработчик/издатель |
| `Series` | string | Серия игр, если есть |
| `CompletionStatus` | string | Статус прохождения из Playnite |
| `InstallSize` | number | Размер на диске в байтах |
| `Source` | string | Библиотека (Steam/GOG/Ручная установка и т.д.) |
| `SteamId` | string | AppID в Steam, если определён |
| `Playtime` | number | Наиграно, **в секундах** |
| `Tags` | string[] | Теги Playnite, включая закодированные технические строки `[Движок] ...`, `[HLTB] ...` |
| `Genres` | string[] | Жанры игры |
| `LastActivity` | string (ISO datetime) \| null | Дата и время последнего запуска игры, `null` если не запускалась ни разу |
| `Links` | {Name, Url}[] | Ссылки на страницы игры |

Важно для дальнейшей обработки: строки вида `[Движок] Unity`, `[HLTB] 12h` внутри `Tags` — это
технические метаданные, а не жанровые теги, и должны исключаться из любых вычислений вкусового
профиля (см. раздел 8.1).

## 7. Источники данных и интеграции

### 7.1 Вишлист: Steam + GOG через ITAD

Автоматизируется только Steam и GOG. Публичного способа читать чужой вишлист в Epic Games Store не
существует ни у кого в принципе (не только у ITAD) — он требует авторизованной сессии самого
пользователя. Учитывая, что основной вишлист и так в Steam, а цены на Epic-эксклюзивы всё равно
видны через ITAD/CheapShark как на обычный магазин (раздел 7.2), Epic сознательно не подключается к
логике вишлиста.

У ITAD есть нативная синхронизация профиля (Settings → Profiles & Data Sources на
isthereanydeal.com), которая подтягивает вишлист напрямую из Steam и GOG (профиль на момент
синхронизации должен быть публичным, дальше его можно закрыть обратно).

**Реализация:**
1. Один раз вручную на сайте ITAD привязать Steam- и GOG-профили (обычная кнопка "Connect" в
   настройках, кода не требует).
2. Один раз локально запустить `scripts/setup_itad_oauth.py` — скрипт открывает страницу входа
   ITAD в браузере (Authorization Code + PKCE, у проекта уже есть Client ID/Secret ITAD), после
   подтверждения доступа получает и печатает `refresh_token`. Этот токен сохраняется как GitHub
   Secret `ITAD_OAUTH_REFRESH_TOKEN` — долгоживущий "пропуск", повторный ручной вход не требуется.
3. `wishlist_parser.py` при каждом запуске обменивает `refresh_token` на временный access-токен
   (`grant_type=refresh_token`) и одним запросом к `/waitlist/games/v1` получает актуальный
   объединённый вишлист из Steam+GOG. Точные названия эндпоинтов/scope нужно свериться с
   актуальной документацией `https://docs.isthereanydeal.com/` непосредственно перед реализацией —
   в спецификации ITAD они могут незначительно меняться со временем.

### 7.2 Цены и скидки

* **ITAD API v2** — основной источник по официальным магазинам:
  * `/games/lookup/v1` — сопоставление Steam AppID/названия с внутренним ITAD ID
  * `/games/prices/v3` — текущие цены по всем официальным магазинам
  * `/games/history/v2` — история цены (основа для графиков)
  * `historyLow` отдаётся на уровне игры и включает минимум за всё время, за 3 месяца и за год
* **CheapShark** — бесплатный, без ключа, кросс-проверка/фолбэк по официальным магазинам (Steam,
  GOG, Epic, Fanatical, GreenManGaming, Humble и др.): эндпоинты `/deals`, `/games`, справочник
  `/stores`.

### 7.3 Магазины ключей (кейшопы) — модульная архитектура

Ни ITAD, ни CheapShark не индексируют серые/кейшоп-магазины (Instant Gaming, Eneba, G2A, Kinguin) —
это осознанная редакционная политика обоих сервисов, а не техническое ограничение. У таких сайтов, как
правило, нет официального API вообще, поэтому это единственное место в проекте, где применяется
веб-скрейпинг — и сразу закладывается расширяемой архитектурой, чтобы позже свободно добавлять новые
сайты без переписывания остального пайплайна.

`scripts/keyshops/base.py` — общий интерфейс для любого сайта:
```python
from abc import ABC, abstractmethod

class KeyshopScraper(ABC):
    name: str                     # человекочитаемое имя, напр. "Instant Gaming"
    request_delay_sec: float = 2  # задержка между запросами (базовая политика вежливости)
    cache_ttl_hours: int = 12

    @abstractmethod
    def search(self, title: str) -> list["Candidate"]:
        """Найти кандидатов-товаров по названию игры."""

    @abstractmethod
    def get_price(self, product_url: str) -> "PriceResult | None":
        """Цена/наличие по прямой ссылке на товар."""
```

`scripts/keyshops/__init__.py` хранит список активных скрейперов (`ACTIVE_SCRAPERS = [InstantGamingScraper()]`).
`price_aggregator.py` просто перебирает этот список — добавление нового сайта в будущем означает
написать один файл, реализующий два метода `base.py`, и добавить его в список, без изменений в
остальном пайплайне.

**Реализация `instant_gaming.py`:**
1. `GET https://www.instant-gaming.com/en/search/?q={название}` — HTML со списком карточек товаров.
2. Выбрать наиболее похожий заголовок по нормализованному сравнению строк (переиспользовать логику
   нормализации из `scripts/utils/normalize.py`, которая портирована из `getNormalizedName` в
   `index.html` — единая логика вместо дублирования на фронте и бэке).
3. Открыть страницу товара и извлечь `<script type="application/ld+json">` — Instant Gaming кладёт
   туда структурированные Schema.org `Product`-данные (`price`, `priceCurrency`, `availability`) —
   это надёжнее парсинга вёрстки напрямую.
4. Кастомный `User-Agent`, задержка между запросами и кеш на 12–24 часа (заданы в `base.py` по
   умолчанию, чтобы каждый новый скрейпер наследовал эти правила автоматически) — личное
   некоммерческое использование одним пользователем не должно превращаться в агрессивный краулинг.

### 7.4 Метаданные для рекомендаций

* **Steam Store API** (`store.steampowered.com/api/appdetails?appids=X`, ключ не требуется) —
  официальные жанры, категории, разработчик/издатель, дата выхода, `metacritic`,
  `recommendations.total`.
* **Steam `appreviews`-эндпоинт** — фактический `%positive` и число отзывов, используется как сигнал
  качества вместо оценок SteamSpy (см. ниже).
* **SteamSpy** (`steamspy.com/api.php`) — источник тегов и оценки владения (`owners`) для генерации
  кандидатов по тегам (`request=tag`). Поле `playtime` и часть скоринговых полей у SteamSpy сейчас
  возвращают недостоверные/нулевые значения — использовать только `tags`/`genre`/`owners`. Жёсткий
  рейт-лимит: 1 запрос/сек для обычных запросов, 1 запрос/60 сек для `request=all` — обязательно
  кешировать в `data/steamspy_cache.json` (TTL 24 часа) и не дёргать чаще раза в сутки один и тот же
  тег.
* SteamPeek не используется — признан ненадёжным источником похожести на этапе исследования проекта.

## 8. Recommendation Engine

Движок формирует **три независимых блока**, не смешивая их в одну ленту: `match` (под вкус),
`discovery` (вне привычного вкуса, но качественное), `developer_watch` (новинки любимых студий).

### 8.1 Профиль вкуса

Вес каждого тега/жанра считается по всей библиотеке из `games.json`. Ключевой принцип: **явная
оценка (`UserScore`) — это стабильное суждение о вкусе и не должна ослабевать со временем или
перечёркиваться статусом прохождения.** Если игра брошена, но оценена высоко — значит, она
понравилась, даже если пользователь не поставил статус "Completed". Давность и статус прохождения
используются только как слабая подсказка **для игр без явной оценки вообще**, где кроме поведения
опереться не на что.

```
Weight(tag) = Σ_{games with tag} Confidence(game) × Signal(game)
```

**`Signal(game)`** — величина в диапазоне [-1, +1]:
* Если `UserScore > 0` (пользователь явно оценил игру):
  `Signal = (UserScore - neutral_score) / neutral_score`, где `neutral_score` — середина шкалы
  0–100 (по умолчанию 50: `UserScore=0`→ не применимо, см. ниже; `UserScore=50` → 0; `UserScore=100`
  → +1). Используется напрямую, **независимо от `CompletionStatus`**.
* Если `UserScore == 0` (оценки нет вообще — это не "0 из 100", а именно отсутствие оценки):
  сигнал берётся из `CompletionStatus` как более слабая догадка:
  * статус из `positive_statuses` (например, `Completed`, `Beaten`) → `unrated_positive_signal`
    (по умолчанию `+0.3`);
  * статус из `negative_statuses` (например, `Abandoned`, `Dropped`) → `unrated_negative_signal`
    (по умолчанию `-0.3`);
  * любой другой статус (`Playing`, `Plan to Play`, `On Hold`) → `0`, решение отдаётся `Playtime`.

  `positive_statuses`/`negative_statuses` — настраиваемые списки в `taste_profile.yaml`, а не
  захардкоженные строки: названия статусов прохождения в Playnite пользователь может переименовать.

**`Confidence(game)`** — насколько сильно доверять сигналу:
* Если `UserScore > 0`: `Confidence = log(1 + Playtime_hours(game))`. **Recency не применяется** —
  явная оценка не "протухает" от того, что игру давно не запускали.
* Если `UserScore == 0`: `Confidence = log(1 + Playtime_hours(game)) × RecencyDecay(game)`. Здесь
  давность оправдана — это лишь косвенный сигнал по поведению, и если игра много лет висит без
  вердикта, её влияние на профиль должно постепенно снижаться.

`RecencyDecay(game) = 0.5 ^ (months_since_last_activity / recency_half_life_months)` — экспоненциальное
затухание с периодом полураспада `recency_half_life_months` (по умолчанию 18), на основе поля
`LastActivity` из `games.json`.

Источник тегов — `Genres` + `Tags` из `games.json`, **за исключением** технических псевдо-тегов
`[Движок] ...` и `[HLTB] ...` — они не отражают вкус и должны фильтроваться до подсчёта весов.

Все параметры формулы вынесены в `taste_profile.yaml` (раздел 6.7) и подстраиваются без правки кода.

### 8.2 Генерация кандидатов (блок Match)

1. Взять топ-`match_top_tags_count` тегов профиля по абсолютному весу.
2. Для каждого — запросить SteamSpy `request=tag` и взять до `match_candidate_pool_per_tag`
   игр-кандидатов (с кешированием, см. 7.4).
3. Добавить кандидатов из Developer/Publisher affinity (раздел 8.5).
4. Исключить всё, что уже есть в `games.json` или `wishlist.json` — сопоставление по
   `steam_appid`, где есть, и по нормализованному названию через `scripts/utils/normalize.py` как
   резервный метод (та же логика, что уже используется в `index.html` для дедупликации демо/полных
   версий).

### 8.3 Скоринг блока Match

Для каждого оставшегося кандидата:

1. Строится TF-IDF вектор по тегам кандидата (частые общесистемные теги вроде "Singleplayer"
   получают низкий вес, специфичные — высокий, за счёт обратной частоты по всему пулу кандидатов).
2. Считается косинусное сходство между этим вектором и вектором профиля вкуса — это база
   `match_score`.
3. Применяется гейт качества: кандидат отбрасывается, если `%positive` Steam-отзывов ниже
   `review_score_threshold` или число отзывов меньше `min_review_count`.
4. Применяется множитель скидки: если игра прямо сейчас продаётся со скидкой (по данным
   `price_cache.json`, если применимо) или на историческом минимуме — итоговый `match_score`
   получает бонус, чтобы выгодные по цене и по вкусу игры поднимались выше.
5. Итоговый список сортируется по `match_score`, топ-N попадает в `recommendations.match` вместе с
   объяснением (`reasons` — теги с наибольшим вкладом в сходство).

### 8.4 Блок Discovery

Отдельная логика, не подмешанная в Match — цель именно "мало похоже на профиль, но может зайти":

1. Кандидаты берутся из тегов, которые представлены в общем каталоге SteamSpy, но **слабо весят**
   в профиле вкуса пользователя (низкий/нулевой `Weight(tag)`) — это жанровые "соседи", а не повтор
   уже освоенного. Итого пул размером `discovery_pool_size`.
2. Отбор внутри пула идёт не по сходству с профилем, а по независимому сигналу качества: высокий
   `%positive` + большое число отзывов Steam, либо попадание в топы SteamSpy по владению
   (`top100in2weeks`/`top100forever`).
3. Диверсификация — упрощённый Maximal Marginal Relevance: при выборе следующей игры в
   `discovery_output_count` штук штрафуется сходство с уже выбранными (по доминирующему тегу), чтобы
   блок не превратился в несколько клонов одной и той же игры. Баланс между "качеством" и
   "разнообразием" регулируется `mmr_lambda`.
4. В выдаче каждая позиция сопровождается честной пометкой (`note`) вида "мало похоже на твою
   библиотеку, но хорошо принято игроками" — без притянутых обоснований в духе Match-блока.

### 8.5 Developer / Publisher affinity (блок Developer Watch)

Отдельный сигнал, не завязанный на теги: если у студии/издателя в библиотеке есть
`developer_affinity_min_games` и более игр с явным `UserScore` заметно выше `neutral_score` —
все новые/анонсированные релизы этой студии автоматически добавляются в `developer_watch`,
независимо от совпадения тегов. Источник новых релизов по разработчику — Steam Store API
(поиск по `developer`/`publisher` среди недавних релизов).

### 8.6 Графики цен

Каждый объект в `recommendations.match`/`discovery` несёт `price_history`, полученный из
`ITAD /games/history/v2` на момент сборки данных. Это позволяет фронтенду рисовать график без
дополнительных запросов к внешним API — сайт остаётся полностью статичным, ключи API не попадают на
клиент.

## 9. Deals Engine

* Для каждой позиции `wishlist.json` запрашиваются: ITAD (`prices/v3` + `history/v2`), CheapShark
  как кросс-чек по официальным магазинам, и все зарегистрированные keyshop-скрейперы из
  `scripts/keyshops/`.
* `must_buy = true`, если текущая цена ≤ `history_low.price` **или** цена у любого кейшопа ниже
  лучшей официальной цены — без автоматической наценки за риск кейшопа, доверие к конкретному сайту
  оценивает сам пользователь на фронтенде.
* Telegram-уведомление по игре отправляется только если выполняется одно из условий:
  * достигнут новый исторический минимум;
  * цена упала ниже последнего уведомлённого значения (`notified_deals.json`);
  * `match_score` игры (если она также есть в рекомендациях) выше порога **и** сейчас скидка.
* Cooldown — не чаще одного уведомления на игру в 48 часов, даже если цена продолжает колебаться в
  этом окне.

## 10. Telegram-нотификатор

* Формат сообщений — MarkdownV2. Обязательно экранировать спецсимволы Telegram
  (`_ * [ ] ( ) ~ \` > # + - = | { } . !`) — MarkdownV2 в Telegram строго проверяет их наличие и
  без экранирования сообщение просто не отправится.
* Если за один прогон пайплайна набралось несколько подходящих скидок — отправляется одно
  дайджест-сообщение со списком, а не серия отдельных пушей.
* Формат одной позиции в дайджесте: название, текущая цена и магазин, % скидки или пометка
  "Исторический минимум", `match_score` и ближайшие похожие игры из библиотеки (если применимо),
  прямые ссылки на покупку (официальный магазин + лучший кейшоп, если есть).

## 11. Фронтенд

Все новые страницы — обычные статические HTML/CSS/JS-файлы, без сборки, в стиле уже существующего
`index.html` (никакого фреймворка/бандлера не требуется).

### 11.1 `index.html`
Не изменяется. Получает обратные ссылки с новых страниц, но сам не содержит никакой навигации на них.

### 11.2 `hub.html` — лендинг/дашборд
Точка входа на весь хаб: карточки-переходы на Библиотеку (`index.html`), Скидки (`deals.html`),
Рекомендации (`recommendations.html`), плюс компактный виджет "Горящие скидки из вишлиста прямо
сейчас" (топ-3-5 позиций из `deals` с наибольшей скидкой/историческим минимумом).

### 11.3 `deals.html` — скидки и вишлист
* Список всех позиций вишлиста с ценами по всем источникам (официальные магазины + все подключённые
  кейшопы).
* Фильтры: только официальные / включая кейшопы, только исторический минимум, сортировка по % скидки.
* У каждой позиции — спарклайн истории цены (Chart.js) и бейджи (`Must Buy`, `%` скидки).

### 11.4 `recommendations.html` — рекомендации
* Три визуально разделённых блока: **Match** (под вкус, с `match_score` и `reasons`), **Discovery**
  (с пометкой почему это здесь), **Developer Watch** (с указанием, какая студия и почему).
* У каждой карточки — график цены (если игра сейчас продаётся) и, где применимо, бейдж скидки.

### 11.5 Общие технические требования
* Общий header/nav-компонент подключается через `assets/shared-nav.js` только в трёх новых
  страницах — `index.html` не модифицируется.
* Графики — Chart.js через CDN.
* Данные загружаются асинхронным `fetch('data/generated_hub.json')`, как и в существующем
  `index.html` для `games.json`.
* Сайт остаётся read-only: изменить вишлист или оценку прямо с сайта нельзя — это осознанно вынесено
  за рамки проекта, поскольку потребовало бы отдельного авторизованного бэкенд-эндпоинта для записи.

## 12. GitHub Actions

`.github/workflows/update_hub.yml`:

```yaml
name: Update Game Hub

on:
  schedule:
    - cron: '0 */4 * * *'
  workflow_dispatch:
  push:
    paths:
      - games.json

jobs:
  update:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'

      - run: pip install -r requirements.txt

      - name: Run pipeline
        run: python scripts/main.py
        env:
          ITAD_API_KEY: ${{ secrets.ITAD_API_KEY }}
          ITAD_OAUTH_REFRESH_TOKEN: ${{ secrets.ITAD_OAUTH_REFRESH_TOKEN }}
          TELEGRAM_BOT_TOKEN: ${{ secrets.TELEGRAM_BOT_TOKEN }}
          TELEGRAM_CHAT_ID: ${{ secrets.TELEGRAM_CHAT_ID }}

      - name: Commit updated data
        uses: stefanzweifel/git-auto-commit-action@v5
        with:
          commit_message: 'Auto-update game hub data'
          file_pattern: 'data/*.json'
```

Пуш от auto-commit-шага сам триггерит редеплой на Vercel — отдельного deploy-шага в workflow не
требуется, в отличие от схемы с GitHub Pages, где нужен явный deploy-экшен.

|---|---|
| `ITAD_API_KEY` | apikey-запросы к ITAD (цены/поиск) |
| `ITAD_OAUTH_REFRESH_TOKEN` | Waitlist sync (Steam+GOG), получается один раз через `setup_itad_oauth.py` |

| `TELEGRAM_CHAT_ID` | ID чата для уведомлений |

## 13. Устойчивость пайплайна

Модули независимы и не должны обрушивать весь прогон целиком:

* Каждый модуль (`wishlist_parser`, `price_aggregator`, каждый keyshop-скрейпер,
  `recommendation_engine`) оборачивает свою логику в try/except на уровне отдельной игры/источника —
  ошибка по одной игре или недоступность одного источника не должна прерывать обработку остальных.
* Если ITAD временно недоступен — использовать последние закешированные значения из
  `price_cache.json` с пометкой `stale: true`, а не падать полностью.
* Если конкретный keyshop-скрейпер начинает падать (например, сайт поменял вёрстку) — пайплайн
  просто пропускает этот источник для всех игр в этом прогоне и логирует ошибку, остальные источники
  продолжают работать.
* В конце прогона `main.py` пишет краткий сводный лог: сколько игр обработано, какие источники
  отработали успешно/с ошибками, сколько уведомлений отправлено — для быстрой диагностики через
  вкладку Actions на GitHub.

## 15. Пошаговый план реализации

Каждый шаг согласовывается перед тем, как переходить к следующему.

1. Настройка ITAD: привязка Steam+GOG профилей на сайте, разовый запуск `setup_itad_oauth.py`.
2. `wishlist_parser.py` → `data/wishlist.json`.
3. `price_aggregator.py`: ITAD `prices/v3` + `history/v2`, CheapShark fallback → `data/price_cache.json`.
4. `scripts/keyshops/` — `base.py` + `instant_gaming.py`.
5. `recommendation_engine.py` — Match + Discovery + Developer Watch, с `taste_profile.yaml`.
6. `telegram_notifier.py` + логика cooldown/дайджеста.
7. `main.py`-оркестратор, сборка `data/generated_hub.json`.
8. Приватизация репозитория (личный аккаунт) + подключение Vercel + `robots.txt`.
9. `hub.html` / `deals.html` / `recommendations.html` + графики цен.
10. `.github/workflows/update_hub.yml`.
11. Финальный сквозной прогон: проверка данных на сайте и Telegram-уведомлений.

## 16. Критерии готовности MVP

* `data/generated_hub.json` собирается автоматически по расписанию и после пуша `games.json`.
* Вишлист из Steam и GOG подтягивается без ручного вмешательства после разовой настройки OAuth.
* По каждой позиции вишлиста видна цена минимум из одного официального магазина и из Instant Gaming.
* `recommendations.match` и `recommendations.discovery` — заметно разные по составу списки, ни один
  кандидат не дублируется в обоих одновременно и не встречается в `games.json`/`wishlist.json`.
* На `recommendations.html` и `deals.html` у карточек отображается график истории цены.
* Telegram получает не более одного уведомления на игру за 48 часов и только при выполнении условий
  из раздела 9.
* Репозиторий приватный, сайт открывается по прямой ссылке на Vercel, секреты нигде не светятся в
  коде или логах.
